По рекомендации в ту же ветку добавлен коммит, на комментарий дан ответ, затем
выполнена повторная проверка:

```text
$ git commit -m "ЛР4: по итогам Code Review имя файла в README сделано ссылкой"
[feature/vlasov 77ad7fc] ЛР4: по итогам Code Review имя файла в README сделано ссылкой
```

> GitHub не даёт автору нажать **Approve** на собственный Pull Request: одобрение
> (**Review changes → Approve** или **Request changes**) ставит другой участник
> команды. Поэтому проверка оформлена комментариями ревью.

## Ответы на контрольные вопросы

**1. Что такое ветка и зачем она нужна?**
Ветка — отдельная линия разработки; технически это указатель на последний коммит
этой линии. Ветки позволяют изолировать изменения: новую функцию или исправление
делают в своей ветке, не ломая рабочую версию в `main`, и несколько человек могут
работать параллельно. Готовые изменения сливаются в `main` через merge.

**2. Что делает команда `git add`?**
Добавляет изменения из рабочей директории в индекс (staging area), то есть отмечает,
что войдёт в следующий коммит. `git add .` добавляет все изменения в текущей папке.

**3. Что делает команда `git commit`?**
Фиксирует содержимое индекса в локальном репозитории как новый коммит — снимок
проекта с автором, датой, сообщением и ссылкой на предыдущий коммит. У каждого
коммита есть уникальный хеш (например, `8f7642b`).

**4. Что делает команда `git push`?**
Отправляет локальные коммиты ветки в удалённый репозиторий (`origin` на GitHub)
и обновляет там эту ветку. Флаг `-u` связывает локальную ветку с удалённой, чтобы
дальше можно было писать просто `git push` и `git pull`.

**5. Что такое Pull Request?**
Запрос на слияние изменений из одной ветки в другую (например, `feature/vlasov` → `main`).
В нём есть описание, список коммитов, вкладка **Files changed** с изменениями,
обсуждение и результаты проверок. После ревью Pull Request сливают кнопкой **Merge**.

**6. Зачем нужен Code Review?**
Чтобы другие участники проверили изменения до слияния: нашли ошибки, проверили
стиль и структуру, отсутствие лишних файлов. Ревью повышает качество кода, помогает
команде знать, что меняется в проекте, и делает ответственность за код общей.
Итог ревью — комментарии, **Approve** или **Request changes**.

**7. Как посмотреть историю изменений?**
Командами `git log`, `git log --oneline` и `git log --oneline --graph --all`
(граф с ветками и слияниями); в VS Code — расширением Git Graph; на GitHub —
во вкладке **Commits**, в разделе **Insights → Network** и в истории Pull Request.
